Article 模块怎么做

目标不是套用完整 DDD，而是让复杂规则有明确归属，同时避免重复 Model 字段和大规模 hydrate / rehydrate。

结论：采用轻量 DDD

先做决策

保留 Domain

状态流转、内容规则、版本发布等真正的业务约束放进 Domain。

不要大 Aggregate

不要复制 Article 全部字段、关联、时间字段，也不要为查询 hydrate 聚合。

Service 负责协调

Service 表达用例并管理事务；Repository 负责查询和落库。

推荐调用流

Controller 接收参数、鉴权
→
Application Service Create / Update / Publish / Reject
→
小型 Domain + Repository
Status Workflow
Content Rules
Revision Rules
列表、详情、搜索属于读操作，Repository 可以直接返回 DTO，不经过 Domain。

Domain 放什么

应该放入

  • 草稿、审核、发布、下线、驳回的状态规则
  • 内容清洗、摘要生成和版本校验
  • 发布权限、当前版本与发布版本的一致性

不应该放入

  • 数据库 Model 的全部字段和关联对象
  • CreatedAt、UpdatedAt 等纯持久化信息
  • 详情 DTO、列表字段和大量无行为 Getter

表与业务边界

数据表建议定位
article文章身份、状态、当前版本 ID、已发布版本 ID。
article_version版本实体；只按用例加载当前版本，不加载全部历史。
article_publish发布历史记录，追加写入。
article_category_rel
article_tag_rel		关系数据，只管理 ID，不放入大聚合。
article_comment
article_stat		独立聚合，避免扩大 Article 的事务边界。
content_type_*独立模块，Article 只引用 ContentType ID。

最小领域对象

type Workflow struct {
    ArticleID          uint64
    Status             Status
    CurrentVersionID   uint64
    PublishedVersionID *uint64
}

func (w *Workflow) Publish(actor Actor) error
func (w *Workflow) Reject(actor Actor) error
func (s Service) CreateDraft(...)
func (s Service) UpdateDraft(...)
func (s Service) Submit(...)
func (s Service) Publish(...)
func (s Service) Reject(...)
func (s Service) Offline(...)
Repository 发布时只查询 Workflow 需要的少数字段。这里允许一次很小的 restore，不再映射完整 Article。

表结构先统一

  • published_version_id 应允许 NULL，草稿创建时还没有发布版本。
  • article.title/summary 与版本表重复，需要确定唯一事实来源。
  • article_version.published、published_version_id、发布记录不要同时表达当前发布状态。
  • 分类关系表是多分类，但旧 DTO 是单个 CategoryID，需要统一。
  • content_type_id 数据库可空，Go Model 也应使用可空类型。

落地顺序

统一数据定义

先对齐 SQL、GORM Model、DTO 的字段和关系。

缩小 Domain

保留 Status、Content、Workflow，移除大 Article 聚合。

分离读写

写操作走规则；查询直接返回 DTO。

按需扩展

规则增长后再扩大 Workflow，不提前设计完整聚合。

一句话方案：用 DDD 管规则，不用 Aggregate 搬运整张表。
