# AI 模块生成指南

本文档用于指导 AI 按照当前项目实际代码、当前数据库结构和当前依赖实现生成业务模块。

> **核心原则：当前项目实际状态优先于历史对话、历史提示词、历史实现和本文档中的示例。**

---

## 可直接使用的提示词

```text
请在当前 Go 项目中生成一个完整的业务模块。

【最高优先级：当前项目实际状态优先】

本提示词描述的是项目当前状态，而不是项目历史。

必须遵循以下规则：

1. 当前工作区中的实际代码优先于本提示词中的任何示例。
2. 当前工作区中的实际代码优先于历史对话。
3. 当前工作区中的实际代码优先于你的既有认知。
4. 不要根据历史对话、历史提示词或历史实现推断当前项目状态。
5. 不要使用当前项目中不存在的文件、函数、类型、接口、字段、目录或 API。
6. 如果本提示词中的某个 API、类型、文件、目录或实现方式在当前项目中不存在，直接忽略该描述，不要尝试恢复、模拟或兼容旧实现。
7. 如果本提示词与当前项目实际代码冲突，以当前项目实际代码为准。
8. 如果无法确认某个实现是否存在，必须先检查当前项目，不允许猜测。
9. 不要因为过去曾经使用过某种方案，就认为当前项目仍然使用该方案。
10. 禁止为了遵循历史提示词而修改当前项目架构。
11. 禁止为了兼容历史实现而增加兼容层、适配层或旧 API。
12. 不要将历史实现、历史 API、历史目录或历史限制重新写入新代码、注释、文档或新的提示词。

【提示词防污染规则】

本项目会持续演进。

因此禁止将以下类型的内容继续写入代码、文档或新的提示词：

- “不要使用旧版 XXX”
- “不要使用 ABCD”
- “以前使用 XXX，现在不要使用”
- “旧版本使用 XXX”
- “XXX 已经废弃”
- “不要恢复之前的实现”
- “之前的实现有问题”
- 任何只对历史版本有效的限制

如果某个历史实现当前已经不存在，不需要提醒 AI 不要使用它。

正确的规则应该是：

“实现前检查当前项目实际存在的 API，并以当前实现为准。”

而不是：

“不要使用旧版 ABCD。”

【当前状态验证】

开始编码前，必须先验证所有将要依赖的关键实现：

- 文件是否存在
- 类型是否存在
- 函数是否存在
- 方法是否存在
- 接口是否存在
- 当前函数签名是什么
- 当前依赖版本是什么
- 当前模块采用什么目录结构
- 当前鉴权 API 是什么
- 当前 Bootstrap / Wire / Provider 注册方式是什么
- 当前 ORM / GORM Gen 使用方式是什么
- 当前数据库表结构是什么

如果提示词中的示例与当前代码不一致：

- 以当前代码为准；
- 不需要修改其他模块来适配示例；
- 不需要兼容示例中的旧实现；
- 不需要在代码中解释旧版本。

---

【数据库结构：强制规则】

数据库表结构必须以：

cmd/migrate/install.sql

为唯一事实来源。

在开始设计 Model、Repository、API 数据结构以及数据库相关代码之前，必须首先读取：

cmd/migrate/install.sql

然后确认当前模块对应的数据表。

必须检查：

- 表名
- 字段名
- 字段类型
- NULL / NOT NULL
- 默认值
- 主键
- 唯一索引
- 普通索引
- 外键
- 字段长度
- 其他数据库约束

Model、Repository 和数据库相关实现必须以 install.sql 中的实际定义为依据。

【禁止根据其他来源推断数据库结构】

禁止根据以下内容推测数据库结构：

- 用户需求
- API 参数
- Go Model
- GORM Model
- GORM Gen 代码
- 历史代码
- 历史对话
- 其他文档
- 模块名称
- 业务常识
- “看起来应该存在”的字段

即使某个字段从业务上看非常合理，只要 `cmd/migrate/install.sql` 中不存在，也不得自行增加。

即使某个字段从业务上看应该存在，只要无法从 `cmd/migrate/install.sql` 确认，也不得自行假设。

【数据库表不存在：立即停止】

如果在：

cmd/migrate/install.sql

中找不到当前模块对应的数据表：

立即停止整个任务。

禁止继续：

- 创建 Model
- 创建 Repository
- 创建 Controller
- 创建 Service
- 创建 GORM Gen
- 修改 cmd/gormgen/main.go
- 修改 Wire
- 修改 Bootstrap
- 创建数据库表
- 创建迁移 SQL
- 推测表结构
- 根据历史代码恢复表结构
- 自行设计数据库结构

必须向用户明确说明：

“在 cmd/migrate/install.sql 中没有找到当前模块对应的数据表，因此无法继续生成模块。请确认数据库表定义或提供对应迁移。”

然后等待用户确认。

【数据库结构冲突：立即停止】

如果数据库表存在，但是以下任意内容存在冲突：

- 需求字段与 install.sql 不一致
- 需求要求的字段不存在
- 需求要求的类型与 install.sql 不一致
- 需求要求 NOT NULL，但数据库是 NULL
- 需求要求 NULL，但数据库是 NOT NULL
- 需求要求默认值与数据库不同
- 需求要求索引，但数据库不存在
- 需求要求唯一约束，但数据库不存在
- 需求要求关联关系，但数据库无法确认

立即停止。

禁止自行修改数据库结构。

必须向用户说明：

1. install.sql 当前定义是什么；
2. 需求要求什么；
3. 两者具体冲突在哪里；
4. 需要用户确认什么。

等待确认后才能继续。

【模块信息】

- 模块名：{module_name，例如 notice}
- 中文名称：{例如 通知管理}
- 路由前缀：/{route_prefix}
- 权限资源名：{permission_resource}

- 数据模型及字段：
  {字段、类型、是否必填、默认值、索引、关联关系}

注意：

这里描述的是业务需求，不是数据库结构事实来源。

实际数据库结构必须以：

cmd/migrate/install.sql

为准。

- 接口：
  {list/detail/create/update/delete 或其他业务操作}

- 业务规则：
  {状态流转、唯一性、删除限制、事务边界等}

- 公开接口：
  {没有则写“无”；禁止自行将接口设为公开}

【开始编码前】

必须严格按照以下顺序执行：

1. 检查当前 Git 工作区状态。
2. 不覆盖用户已有的无关修改。
3. 读取 cmd/migrate/install.sql。
4. 查找当前模块对应的数据表。
5. 如果表不存在，立即停止并向用户确认。
6. 如果表存在，完整检查该表的结构。
7. 检查相关索引、关联表和约束。
8. 找到当前项目中与目标模块最接近的实际业务模块。
9. 阅读该模块当前实际代码。
10. 检查当前鉴权 API。
11. 检查当前 Bootstrap / Wire / Provider。
12. 检查当前 GORM Gen 使用方式。
13. 检查当前项目 Go 版本及相关依赖。
14. 确认以上信息后，再开始编码。

选择参考模块时，不要机械使用固定模块。

参考模块优先级：

1. 当前项目中与目标业务最接近且正在使用的模块；
2. 当前项目中最近采用的同类模块；
3. 当前项目公共基础设施的实际实现；
4. 本提示词中的示例。

如果示例与当前代码冲突：

以当前代码为准。

---

【目录结构】

根据当前项目中正在使用的模块结构创建。

不要因为本提示词给出了固定目录，就强制创建当前项目已经不再使用的目录或文件。

例如当前项目仍采用：

internal/app/{module_name}/
├── api/
│   ├── {module_name}.go
│   └── swagger.go
├── errno/
│   └── errno.go
├── model/
│   ├── {module_name}.go
│   └── {module_name}_test.go
├── controller.go
├── service.go
└── repo.go

则遵循当前项目实际结构。

只有业务确实需要时才增加其他文件。

不要引入当前项目没有采用的新分层框架。

---

【Model】

1. Model 必须与 cmd/migrate/install.sql 中的真实表结构一致，禁止使用 `foreignKey` / `referenceKey` 以外的 tag。
2. 字段名必须与数据库实际结构一致。
3. 字段类型必须与数据库实际结构一致。
4. NULL / NOT NULL 必须与数据库实际结构一致。
5. 默认值必须与数据库实际结构一致。
6. 索引和唯一约束必须以数据库实际结构为准。
7. 公共字段是否复用项目公共类型，以当前代码实际方式为准。
8. 受业务约束的字段可以通过模型方法进行设置。
9. 模型方法必须先校验，成功后再修改字段。
10. 业务校验错误使用当前项目实际采用的 errno 机制。
11. 为关键模型规则编写测试。
12. 不得自行增加数据库字段。
13. 不得自行删除数据库字段。
14. 不得自行修改数据库字段类型。
15. 不得自行修改 NULL / NOT NULL。
16. 不得自行增加数据库索引。

---

【API】

1. 请求参数按照当前项目实际 API 风格定义。
2. ID、分页以及其他公共类型优先复用当前项目已经存在的类型。
3. JSON 字段名必须符合当前接口约定。
4. Swagger 注解必须与实际 API 一致。
5. DTO、路由、请求参数和返回值必须保持一致。
6. 不要为了方便改变当前项目已有的公共 API 约定。

---

【Service】

1. Service 的设计必须遵循当前项目实际结构。
2. 如果当前项目通过 Service 内部定义 Repository 接口，则继续采用该方式。
3. Service 不直接依赖 Gin，除非当前项目已有明确约定。
4. Service 负责业务校验。
5. Service 负责资源存在性检查。
6. Service 负责对象构造。
7. Service 负责业务编排。
8. 使用 Model 的业务方法修改受约束字段。
9. 多步骤写操作必须明确事务边界。
10. 不得自行引入当前项目没有使用的架构模式。

---

【Repository】

1. Repository 必须遵循当前项目实际使用的 GORM / GORM Gen 方式。
2. 数据库操作必须遵循当前项目的 Context 传递方式。
3. 列表查询、分页、排序和过滤必须复用当前项目已有工具。
4. Update 必须明确限制允许修改的字段。
5. 多表写操作遵循当前项目实际事务机制。
6. 禁止手工修改 GORM Gen 自动生成文件。
7. 不得根据业务需求自行创造 install.sql 中不存在的数据库字段。
8. 不得根据 Model 反向修改数据库设计。

---

【Controller】

1. Controller 必须遵循当前项目实际 HTTP 层实现。
2. 鉴权必须使用当前项目真实存在的 API。
3. 每条路由的权限策略必须明确。
4. 不得自行将接口设为 Public。
5. 请求绑定必须遵循当前项目实际方式。
6. 错误处理必须遵循当前项目实际方式。
7. 响应格式必须遵循当前项目实际方式。
8. Swagger 注解必须与实际代码一致。

---

【GORM Gen】

如果当前项目使用 GORM Gen：

1. 按当前项目实际方式注册 Model。
2. 使用当前项目实际的 GORM Gen 生成命令。
3. 禁止手工修改 *.gen.go。
4. 生成前检查生成目录是否存在需要保留的手工修改。
5. 如果生成失败，报告具体错误。
6. 不要为了修复生成错误而修改无关模块。

---

【Wire / Bootstrap / Provider】

如果当前项目使用 Wire：

1. 按当前项目真实 Provider 结构注册。
2. Repository 注册方式以当前代码为准。
3. Service 注册方式以当前代码为准。
4. Controller 注册方式以当前代码为准。
5. 如果存在 ControllerSet，则同步更新。
6. 使用当前项目真实的 Wire 生成命令。
7. 不要根据历史 Wire 结构猜测当前 Provider。
8. 不要恢复已经不存在的 Provider。

---

【修改范围】

只修改完成当前模块所必需的文件。

禁止：

- 顺手重构其他模块；
- 修改无关代码；
- 清理与本任务无关的旧代码；
- 为了统一风格修改整个项目；
- 恢复历史实现；
- 添加旧版本兼容层；
- 创建数据库表；
- 修改数据库结构；
- 修改 cmd/migrate/install.sql；
- 修改与当前模块无关的公共代码。

如果发现现有代码存在问题，但该问题不是完成当前模块所必需的：

记录到最终输出，不要自行修复。

---

【验证】

完成后执行当前项目实际适用的：

- gofmt
- GORM Gen
- Wire
- 模块单元测试
- 相关测试
- 必要的全量测试
- 必要的全量构建

如果验证失败：

1. 判断是否由本次修改导致。
2. 如果由本次修改导致，修复并重新验证。
3. 如果属于项目原有问题，不要顺手修复无关代码。
4. 明确区分：
   - 本次修改引入的问题；
   - 项目原有问题。

---

【最终输出】

只报告当前实际发生的事情：

1. 新增文件。
2. 修改文件。
3. 删除文件。
4. 实际使用的数据库表。
5. 实际使用的数据库字段。
6. 路由。
7. 权限。
8. GORM Gen 变更。
9. Wire / Bootstrap 变更。
10. 执行的验证命令及结果。
11. 发现但没有修改的既有问题。
12. 尚未解决的风险或前置条件。

禁止在最终输出中重复：

- 已经不存在的旧实现；
- 已经不存在的旧 API；
- 已经不存在的旧目录；
- 历史提示词；
- 历史兼容方案；
- “不要使用 XXX”形式的历史提醒。

如果任务因为数据库表不存在或数据库结构冲突而停止：

只输出：

1. 检查的 SQL 文件；
2. 是否找到对应表；
3. 当前数据库结构；
4. 发现的问题；
5. 需要用户确认的内容。

不要继续生成代码。

【最终停止条件】

以下任意情况发生时，必须停止编码并向用户确认：

- cmd/migrate/install.sql 中不存在对应表；
- 无法确定模块对应哪张表；
- 需求字段与数据库字段冲突；
- 需求类型与数据库类型冲突；
- 需求 NULL / NOT NULL 与数据库冲突；
- 需求默认值与数据库冲突；
- 需求索引与数据库冲突；
- 需求关联关系与数据库结构无法确认；
- 当前项目存在多个互相冲突的实现，无法确定应该遵循哪一个；
- 当前代码和需求存在无法自动解决的架构冲突。

除非用户确认，否则不得自行做决定。
````
