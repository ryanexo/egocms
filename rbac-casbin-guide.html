RBAC + Casbin 用户 / 角色 / 菜单 / 权限 / 接口逻辑链
总览 表职责 Casbin 策略 菜单展示 接口鉴权 角色授权 角色继承 落地模型

把用户、角色、菜单、权限、接口串成一条可执行的业务链

数据库维护“有哪些东西可以配置”，Casbin 维护“谁实际拥有权限”。 前端菜单展示和后端接口鉴权都走 Casbin，只是资源类型不同。

建议把系统拆成两层：业务表负责配置资料，Casbin 负责运行时授权事实。

用户 user登录主体，最终发起菜单查询和接口请求。
角色 role用户的权限集合载体，可继承其他角色。
菜单 menu控制页面、目录、前端路由是否展示。
权限 permission系统中已创建好的接口权限点目录。
接口 API由 resource + action 描述，例如路径 + 方法。
Casbin运行时唯一鉴权来源，返回允许或拒绝。
用户 user
  -> 绑定角色 role
  -> 角色通过 Casbin 继承其他角色
  -> 角色被授予菜单访问权
  -> 角色被授予菜单下的接口权限
  -> 前端按菜单授权展示页面
  -> 后端按接口权限拦截请求
关键原则 数据库不要承担运行时鉴权查询。运行时判断能不能看菜单、能不能调接口，只查 Casbin。
表 / 字段 职责 运行时是否直接鉴权
user 账号资料。role_id 可作为用户主角色记录，但需要同步到 Casbin 的 g 关系。 否
role 角色基础信息，例如名称、描述。 否
menu 菜单、目录、页面、路由、图标、排序、是否显示等元数据。 否，菜单是否可见查 Casbin
menu_context 菜单树闭包表，便于查祖先、子孙、补齐父级目录。 否
permission 已创建好的权限点目录。通过 menu_id 归属到页面，通过 resource + action 对应接口。 否，接口是否允许查 Casbin
casbin_rule Casbin adapter 自动创建。保存用户-角色、角色继承、角色-菜单、角色-接口授权策略。 是
permission 表的定位 它是“可授权权限点目录”，不是运行时鉴权表。角色授权时只能从这里选择已创建好的权限。

用户绑定角色时，同步写入 Casbin 的 g 规则。

g, user:1, role:admin

角色继承关系也使用 g。Casbin 会自动处理继承后的权限。

g, role:editor, role:viewer
g, role:admin, role:editor

菜单访问权建议使用独立资源命名，例如 menu:{id}，动作固定为 view。

p, role:editor, menu:12, view

接口权限可以直接使用 HTTP 路径和方法，便于中间件拦截。

p, role:editor, /api/articles, GET
p, role:editor, /api/articles, POST
p, role:editor, /api/articles/:id, PUT
p, role:editor, /api/articles/:id, DELETE
统一模型 菜单和接口都可以抽象成 sub, obj, act：用户或角色是 sub，资源是 obj，动作是 act。
查询可见菜单从 menu 查询 visible = 1 的菜单元数据。
查询 Casbin 授权获取当前用户或其角色拥有的 menu:{id}, view 策略。
过滤菜单只保留用户有 view 权限的菜单。
补齐父级如果子菜单有权限但父目录未直接授权，可用 menu_context 补齐父级容器。
组装树返回按 parent_id 或闭包表组装成前端菜单树。
Enforce(user:1, "menu:12", "view") == true
  -> 展示菜单 12

Enforce(user:1, "menu:13", "view") == false
  -> 不展示菜单 13

每个受保护接口进入业务 handler 前，由中间件执行 Casbin 判断。

sub = "user:当前用户ID"
obj = 当前请求资源，例如 "/api/articles"
act = 当前请求动作，例如 "GET"

allowed = casbin.Enforce(sub, obj, act)

allowed == false -> 返回 403
allowed == true  -> 继续执行业务逻辑

菜单权限页面入口

p, role:editor, menu:12, view 只说明该角色可以看到或进入菜单页面。

接口权限增删改查

p, role:editor, /api/articles, GET 才说明该角色可以请求文章列表接口。

只勾选菜单的结果 用户可以看到菜单页，但页面内请求列表、创建、更新、删除等接口时，如果没有对应接口策略，后端返回 403。
查询菜单树从 menu 读取页面、目录、路由等配置。
查询权限目录从 permission 读取已创建好的接口权限点。
权限挂到菜单下按 permission.menu_id 把接口权限展示在对应菜单页面下。
查询当前策略回显从 Casbin 读取该角色已有的 p 策略，回显菜单和权限勾选状态。
提交后校验后端校验提交的 menu_ids 和 permission_ids 必须真实存在。
重写授权策略删除该角色旧的菜单/接口 p 策略，再写入新的 Casbin 策略。
勾选菜单 12:
  p, role:editor, menu:12, view

勾选 permission.id = 8:
  permission.resource = /api/articles
  permission.action   = GET

写入 Casbin:
  p, role:editor, /api/articles, GET

角色继承也是 g 关系。假设 admin 继承 editor，editor 继承 viewer：

g, role:editor, role:viewer
g, role:admin, role:editor

p, role:viewer, menu:10, view
p, role:editor, /api/articles, POST

Enforce(user:1, "menu:10", "view")        -> true
Enforce(user:1, "/api/articles", "POST")  -> true
授权页面提示 回显时可以区分“直接拥有”和“继承获得”。直接拥有允许取消；继承获得通常需要去上级角色调整。

数据库负责

有哪些用户、角色、菜单、权限可以配置；角色授权页面的数据来源；权限点是否允许被选择。

Casbin 负责

用户属于哪个角色、角色继承关系、角色拥有的菜单访问权、角色拥有的接口访问权。

菜单资源

使用 menu:{id} 作为资源，view 作为动作。

接口资源

使用 permission.resource 和 permission.action 对应后端路由拦截。

数据库 = 权限配置资料库
Casbin = 运行时授权事实库

菜单展示:
  Enforce(user, "menu:{id}", "view")

接口鉴权:
  Enforce(user, resource, action)
